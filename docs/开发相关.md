# Project Directory Overview
This section explains the main directories of the project (second-level subfolders are not fully listed).
- addons: Plugins directory, mainly using the RGa_PVZ and anim_player_refactor plugins to process animations
- animation: Animation directory, stores all animation files; most animations are saved individually as .tres files, a few are saved inside scene files
- assets: Assets folder, contains image/audio material, etc. <mark>Due to copyright concerns, this folder has been removed from GitHub — join the QQ group or get the full project content from the intro of a major update video</mark>
- data: Mainly stores Theme resources and data files (almanac/encyclopedia data)
- docs: Documentation directory, stores project documentation (e.g. [Bullet Documentation](子弹说明文档.md))
- readme_show: Images used in the README
- resources: Resources folder
- - character_resource: Character-related resource folder: body HP-change states \ plant planting conditions <mark>(plant-condition resources must be stored in this directory)</mark>
- - crazy_dave_resource: Crazy Dave dialogue resources
- - <mark>level_date_resource: Level configuration resource files</mark>
- scenes: Scene files
- scripts: Script files
- - autoload: Globally autoloaded scripts
- - bullet: Bullet scripts
- - character: Character scripts (zombies \ plants \ components)
- - resources: Custom resource scripts (levels \ plant planting conditions \ Crazy Dave dialogue \ body-change states)
- shaders: Shader scripts
- shader_material: Material files, stores the material settings used when zombies emerge from the ground

# Testing
Running a game scene file directly will use the exported parameter file from that scene, and cards have no cooldown. You can test relevant parameters (sun, speed, deleting zombies) by modifying the MainGame node.

# Plant/Zombie Animation
Use [R2Ga_PVZ](#r2ga_pvz) to convert Plants vs. Zombies animation files into a format supported by the Godot engine.

Zombie animation:
- Use the [anim_player_refactor](#anim_player_refactor) plugin to delete certain tracks — mainly the visible tracks related to the zombie's arms and head. When a zombie loses its arm or head, control visibility via code instead.
- Alternatively, wrap any node that needs code-controlled hiding in a new parent Node2D, and control its show/hide via code, without modifying the animation file (recommended).

Plant animation:
- The blink node used while shooting differs from the blink node used while idle. Since the shooting-blink animation needs to use a visible track, use the [anim_player_refactor](#anim_player_refactor) plugin to delete the visible track on the idle-blink node, and control plant blinking via code instead.

# Bullets

For the full scene/script inheritance structure, movement components, `init_bullet` parameters, and steps to add a new bullet, see the **[Bullet Documentation](子弹说明文档.md)**.

## Bullet Types
Bullets fall into 4 categories: straight-line \ parabolic \ homing \ other (cannon).
### Straight-line
Straight-line, non-piercing attack bullets. When colliding with a roof slope, checks whether the bullet should shatter.

### Parabolic
Parabolic bullets use a Bezier curve to control the trajectory, determining the end point based on the target zombie's position. They can follow the zombie as it moves; once the zombie moves beyond a certain limit, the final landing point is locked in place.

### Homing
Homing bullets update their movement direction every frame based on a Bezier curve.

### Cannon Bullets
Cannon bullets inherit from Node2D and have no inheritance relationship with the base bullet class.

## Bullet Impact Fragment Splash
- Create a GPUParticles2D
- texture (GPUParticles2D): add the bullet-fragment texture atlas
- material (CanvasItem): add a CanvasItemMaterial
	- Adjust the corresponding `particles_anim_h_frames` and `particles_anim_v_frames`
- process_material (GPUParticles2D): add a ParticleProcessMaterial
	- Adjust Display → Animation → Offset
- Adjust particle-effect properties (initial direction, gravity, time scale)

# Collision

## Collision Detection

### Sloped Maps
Character hurtboxes are split into two categories: the detection hurtbox and the real hurtbox.
Non-sloped (non-roof) maps: the detection hurtbox and real hurtbox overlap.
Sloped (roof) maps:
- Two layers are defined: the real layer & the detection layer (their positions differ on a slope)
- - Detection layer: a horizontal line for each row, a straight line where hurtboxes and attack-detection boxes live. On a slope, the character's root node moves according to the slope, while the component on the detection layer moves back to its original position.
- - Real layer: the layer the character's root occupies on a sloped map. On a slope, the character root moves according to the slope, and bullets check the real hurtbox when attacking enemies.
For explosion components, the detection box is generally on the detection layer while the explosion VFX is on the real layer and does not move.

Except for bullet target detection \ the row-independent attack component's straight-line plant bullet (Starfruit) \ the lawn-mower's zombie detection (which all use the real-layer hurtbox), all other detection uses the detection-layer hurtbox.

### Detection Filtering
When checking collisions, the character's "attackable" status is checked at the same time:
  If the attacker can detect that the target is in an attackable state, it emits an "can attack" signal.
  If it cannot attack, it connects to the target zombie's state-change signal, and re-evaluates whether it can attack whenever that state changes.

Plants:
```gd
enum E_BeAttackStatusPlant{
	IsNorm = 1,		## Normal
	IsFloat = 2,	## Floating
	IsDown = 4, 	## Ground spike
	IsShort = 8, 	## Short plant (for filtering zombie-side bullet detection; unused since no zombie-side straight-line bullets exist)
}
```
Zombies:
```
enum E_BeAttackStatusZombie{
	IsNorm = 1,		## Normal
	IsJump = 2,		## Jumping
	IsDownPool = 4,		## Underwater
	IsSky = 8,			## Airborne
	IsDownGround = 16,	## Underground
	IsJumpInPool = 32,	## Jumping into the pool — this state cannot be intercepted by Tall-nut
}
```

## Collision Layers
- layer 1 World: The world layer — house area \ pool collision \ roof slopes
- layer 2 PlantHurtBoxDetection: The plant layer, where plants live
- layer 3 ZombieHurtBoxDetection: The zombie layer, where zombie bodies live
- layer 4 BulletFromPlant: The layer where plant bullets live
- layer 5 ZombieHurtBoxDetectionOnAttack: The zombie's hurtbox layer while attacking. Overlaps with the body hurtbox when not attacking; moves forward while attacking. Detectable by certain special plants (Squash \ Chomper)
- layer 6 ZombieHurtBoxDetectionBeHypnotized: The layer hypnotized zombies are moved to; plant bullets cannot detect this layer
- layer 7 Bowling: The bowling-bullet layer; Pole Vaulting Zombies can detect this layer to jump over it
- layer 8 BulletFromZombie: The layer for zombie bullet areas (unused)
- layer 9 PlantHurtBoxReal: The plant's real hurtbox area
- layer 10 ZombieHurtBoxReal: The zombie's real hurtbox area
- layer 11 ZombieHurtBoxRealBeHypnotized: The real hurtbox area for hypnotized zombies
- layer 12 ItemDetect: Item detection layer (ladders, brains, etc.)
- layer 13 ItemReal: Item's real layer

# Plant Planting
There are four plant placement positions: `float (floating plants: Coffee Bean)`, `down (base/bottom plants: Flower Pot, Lily Pad)`, `norm (normal plants: Peashooter)`, `shell (shell-type plants: Pumpkin)`.
There are 6 terrain types (a plant cell is one of these types + "none"): `"1 None", "2 Grass", "4 Flower Pot", "8 Water", "16 Lily Pad", "32 Roof/Bare Ground"`.

A plant's valid planting terrain can be a combination of multiple types — e.g. Peashooter: `22 = 2 (Grass) + 4 (Flower Pot) + 16 (Lily Pad)`.
A plant's placement-position attribute can only be one value.

## Plant Planting Conditions
Each plant's planting condition uses a custom resource (`ResourcePlantCondition`); plants with identical conditions can share the same resource.
Planting-condition resources must be stored under `res://resources/plant_resource/plant_condition/`.

Plant planting conditions are split into special and non-special:
Purple-card plants are generally non-special.
Special plants must override the corresponding resource script and rewrite the special-plant planting-condition function.
For special purple-card plants (Cob Cannon), whether they can be planted is determined purely by the special-plant judgment function — the purple-card judgment function is not used.
Only Cob Cannon has a dedicated resource script for double-cell plants; extending this requires writing a corresponding resource script.

## Plant Cell
The plant cell (`PlantCell` class) manages the plant(s) currently in that cell.
For normal plants, planting requires both a free position in the plant cell and a matching terrain type.
Special plants must inherit the planting-condition resource script and override the judgment function to determine plantability.

Each plant cell has a container node per position, acting as the parent for planted plants.
The original PlantCell node structure:
- PlantCell (PlantCell)
  - PlantDownContainer (Node2D)
  - PlantFloatContainer (Node2D)
  - PlantNormContainer (Node2D)
  - PlantShellContainer (Node2D)

In this project, plants in the norm and shell positions can follow the up/down movement of a plant in the down position (in the original game, a plant no longer moves after being placed in a flower pot — I only discovered this after finishing, so it stays as is).
A plant in the down position needs a container node (DownPlantSelfContainer) to act as the parent for plants in the norm and shell positions; moving the down plant's container node causes the norm/shell plants to move along with it (using animation or a tween to control the movement).
When planting a down-position plant, the plant cell's norm and shell container nodes become children of the down plant's container node.
Down-position plant node structure:
- DownPlant (Plant)
	- DownPlantSelfContainer (Node2D)
	- DownPlantOtherNode

After planting a base plant, the structure looks like this:
- PlantCell (PlantCell)
  - PlantDownContainer (Node2D)
	- DownPlant (Plant)
		- DownPlantSelfContainer (Node2D)
			- DownPlantOtherNode
			- PlantShellContainer (Node2D)
			- PlantNormContainer (Node2D)
  - PlantFloatContainer (Node2D)

## Possible Pitfalls
- 1. A plant needs a corresponding planting-condition resource file, and the corresponding PlantInfo entry needs to be updated in the global script.
- 2. In the static-fog `_ready()` function, `init_static_fog()` is called to initialize static fog, which deletes any static fog outside of `@export var del_fog_postion_area:Vector2 = Vector2(650, 700)`. If you change the screen display size, you need to adjust this parameter to fit the screen.

# <mark>Creating a New Character (Plant/Zombie)</mark>
- All character scenes inherit from `res://scenes/character/character_000_base.tscn`.
- - Plant scenes inherit from `res://scenes/character/plant/plant_000_base.tscn`.
Base plants that change terrain inherit from `res://scenes/character/plant/plant_000_down_base.tscn`.
- - Zombie scenes inherit from `res://scenes/character/zombie/zombie_000_base.tscn`.
- After creating a new character scene, update the corresponding character type (`plant_type` \ `zombie_type`).

## New Zombies
Create a new inherited scene from `res://scenes/character/zombie/zombie_000_base.tscn`.
<mark>Highlighted sections below indicate nodes that must be modified for every zombie.</mark>
### <mark>Animation Method-Call Tracks:</mark>
- At the start of any movement animation, add a method-call track for: `MoveComponent._walking_start()`
- At the end of the death animation, add a method-call track for: `Zombie000Base._fade_and_remove()`
- At the moment of attack in the attack animation, add a method-call track for: `AttackComponent.attack_once()`
- In non-moving animations, delete the ground position track; use an AnimationTree to control animation switching, and set the `deterministic` property to false so transition animations don't blend the ground position track.
- Ground-movement issue and fix:
- - When each animation ends, it emits `animation_finished` and stops movement. If the next animation is a movement animation with a transition time, the first movement animation ends up stopped.
 Fix: set the previous animation to loop (so it doesn't emit `animation_finished`), and set the transition property `break_loop_at_end = true`.
- - If both the animation before and after a switch involve movement, the character moves briefly/quickly during the switch. Fix by stopping movement during the transition interval (see the Ladder Zombie's fall-from-ladder animation).

### Shadow:
- The zombie's shadow.
### <mark>Body:</mark>
- The zombie's body. Put all of the zombie's sprite nodes under the `BodyCorrect` node; move `BodyCorrect` to correct its position. The `Body` node's position defaults to (0,0) — you don't need to move `Body`'s position when resizing the character.
- Stores dropped heads \ arms \ armor; the corresponding drop item is activated on drop. This is just an organizational folder and doesn't need to be under this node — the `ZombieDropBase`-type node's position must be Vec(0,0), and its child nodes' positions correspond to the relevant body positions.
- Body: Map properties modify Body's position, e.g. pool \ roof slope.
- BodyCorrect: When the zombie character itself moves its body, modify BodyCorrect's position — e.g. jumping \ bungee \ imp-throwing.

### <mark>HP-Stage-Change Component (HpStageChangeComponent):</mark>
- Updates the body's/armor's HP thresholds.
- Defaults to a new stage every third of HP.
- 1. The body's HP has 2 thresholds by default — you need to add two corresponding resource files to the `body_change` list for losing an arm and losing a head.
- 2. Armor HP has 3 thresholds by default — you need to add 3 corresponding armor-state-change resource files to `body_change_armor`.
- If HP doesn't change in exact thirds, you need to assign `boundary_value_hp`.
- Plants using this component must assign `boundary_value_hp`.
### <mark>HP Component (HpComponent):</mark>
- Updates the zombie's body HP \ armor HP.
### <mark>Charred Component (CharredComponent):</mark>
- Place the corresponding charred/burnt animation under this node's position-correction node (the generic charred animation can simply be copied over).
### Attack Component (AttackComponent):
- Generic attack component; drains plant HP every frame.
### Attack Detection Component (DetectComponent)
- A child component of the attack component; handles detection.
- - Detecting a zombie: nothing special.
- - Detecting a plant: gets the plant that should be hit in the current plant cell, in priority order: Shell → Norm → Down.
- For throwing-type attacks, call `update_first_enemy()` to get the leftmost enemy.

### Move Component (MoveComponent):
- Choose `move_mode` as `ground` or `speed` depending on the movement type.
### Swim Collision Box Component (SwimBoxComponent):
- Detects whether the zombie has collided with the pool, triggering swimming behavior.
### Hurtbox Component (HurtBoxComponent):
- Adds an attack-time hurtbox; while attacking, this hurtbox moves forward. Certain special plants (Chomper, Squash) can detect it.
### Drop-Item Component (DropItemComponent):
- On death, determines whether to drop an item (gold/silver/diamond \ garden plant).

# <mark>Fusion Plants</mark>
A fusion plant is created when a plant is already planted on the field, and a different plant that has a "fusion recipe" with it is planted in the same cell — the two plants merge and are replaced by a single new fusion plant that has the abilities of both (e.g. **Sun Pea** = Sunflower + Peashooter, **Coin Pea** = Peashooter + Marigold).

## How It Works
- Fusion-plant scenes/scripts inherit from `res://scripts/character/plant/plant_fusion_base.gd` (the `PlantFusionBase` class, which inherits from `Plant000Base`).
- `PlantFusionBase` provides a `fusion_components` array. Subclasses only need to populate this array (in `_ready()`, after calling `super()`) with the components that should react to this plant's speed-affecting effects (slow, freeze, buffs, etc.). `ready_norm_signal_connect()` automatically connects the `signal_update_speed` signal to each component's `owner_update_speed()` method, so you don't need to repeat the same signal-wiring boilerplate for every fusion plant.

## <mark>Steps to Create a New Fusion Plant</mark>
1. **Register the plant type**: Add a new entry under the `# Fusion Plants` group in the `CharacterRegistry.PlantType` enum, e.g. `P100SunPea = 100`.
2. **Register the fusion recipe**: Add `Vector2i(existing_plant, incoming_plant): fusion_result` to the `AllPlantFusion` dictionary. <mark>Both directions must be added</mark> (fusion should trigger regardless of which of the two plants is planted first), e.g.:
```gd
Vector2i(PlantType.P002SunFlower, PlantType.P001PeaShooterSingle): PlantType.P100SunPea,
Vector2i(PlantType.P001PeaShooterSingle, PlantType.P002SunFlower): PlantType.P100SunPea, ## Also fuses in reverse
```
3. **Register plant info**: Add the corresponding entry to the `PlantInfo` dictionary (PlantName, CoolTime, SunCost, PlantConditionResource, PlantScenes). The planting-condition resource can generally reuse a normal terrain resource (e.g. `000_common_plant_land.tres`).
4. **Create the scene**: Create a new scene inheriting from `plant_fusion_base.tscn`, and copy over the relevant component nodes (e.g. AttackComponent, CreateSunComponent) directly from the two original plant scenes that make up this fusion, as child nodes.
5. **Create the script**: Create a new script inheriting from `PlantFusionBase`. Use `@onready` to reference the component nodes copied over in the previous step, and in `_ready()`, after calling `super()`, populate `fusion_components` with the components being used.

Example (Sun Pea = Peashooter + Sunflower; see `plant_100_sun_pea.gd` for reference):
```gd
extends PlantFusionBase
class_name Plant100SunPea

@onready var attack_component: AttackComponentBulletBase = $AttackComponent
@onready var create_sun_component: CreateSunComponent = $CreateSunComponent

func _ready() -> void:
	super()
	fusion_components = [attack_component, create_sun_component]
```
If a fusion plant needs extra special-case logic (e.g. special behavior in "I am the Zombie" mode), override `ready_norm()`, `_be_zombie_eat_once_special()`, `character_death()`, etc. as needed — again, see `plant_100_sun_pea.gd` for reference.

## When Fusion Is Triggered
Fusion is checked and triggered in the following places:
- **Normal planting** (`plant_cell.gd`'s `create_plant()`): When planting a plant, if the target cell's corresponding position already has a plant, and a fusion recipe exists between it and the plant being planted, the original plant is removed first (via `character_death_disappear()`), and the fusion-result plant is created instead.
- **Moving a plant with the glove** (`hm_glove.gd`'s `_try_place_down()`): When using the glove to pick up an already-planted plant and place it onto a cell containing another plant, fusion is likewise checked and triggered.
- **Planting-condition check** (`condition_000_plant_base.gd`'s `judge_is_can_plant()`): Normally, an occupied position at the target cell would immediately be judged unplantable. However, if the existing plant at the target position has a fusion recipe with the plant being planted, planting is allowed to proceed (fusion is then actually carried out by the two locations above).

## <mark>Notes</mark>
- The fusion-result plant fully replaces both original plants; <mark>the new fused plant's HP, position, and other state are recalculated from their initial values — they are not inherited from the original plants</mark>.
- Fusion currently only supports fusing two plants occupying the same `place_plant_in_cell` position (e.g. both in the Norm position). Cross-position fusion between shell (Shell), base (Down), and floating (Float) positions is not currently supported.
- When adding new fusion recipes, be mindful of balancing the fusion result's sun cost and cooldown time, to avoid the fused plant's stats being far stronger than the original cards' strength.

# Cards
All cards live in the all_card scene, which is autoloaded (AllCard).
When the game creates a card, it copies the corresponding card from AllCard.
When creating a card in an alternate card slot, the CardInBeCard scene file is used, with parameters passed in (Card) to create it.
A card's static character preview is located under Card/CardBg/CharacterStatic — adjust the character's Position property to the correct position.

# Iron Objects
There are two types of iron objects: `IronNode` and `IronNodeArmor` (`IronNodeArmor` inherits from `IronNode`).
An iron object is a new node copied from Body, hidden by default. When an iron object is pulled away by a Magnet-shroom, a new copy of the iron object is made at the same position, which is then pulled away.

# Characters (Plants and Zombies)
The character (plant/zombie) root node only handles base attributes, animation, body-related logic, and a small number of special character features (simple ones, or ones tightly coupled with the character itself and hard to split out) — e.g. potato-mine arming, Chomper's attack, hypnosis. Everything else is handled by components (attack \ attack-detection \ movement \ sleep, and other base components).
Signal connections must be made in the character body itself, except for dependent components (e.g. the attack-behavior component and the attack-detection component).

**In the character's `_ready()` function, initialization is always dispatched based on the initialization type. Inherited plants and zombies should not override `_ready()` — instead, override `init_norm()` for initialization.**

Before a character is added to the tree via `add_child()`, use `init_*()` functions to assign character-related parameters (row, initialization type, etc.).
Zombies should always be created using ZombieManager's `create_norm_zombie()` function.
Certain globally-used main-game data (plant cells \ zombie rows, etc.) live in the autoload singleton MainGameDate, and are updated by the corresponding sub-manager each time the main game scene loads.

## Component Signal Connections
To avoid signals flying everywhere uncontrolled, character and component signal connections must follow these rules (for the character class's own signals):
- The character class's own Timer node's `timeout` signal can be connected directly in the editor. A component's own Timer signal must be connected to that component's own body node.
- A component's custom signal can be connected by its parent component to its child's signal, e.g.:
  - Attack component (parent) → Attack-detection component (child)
- For components that affect the character's speed, add the component to the character root node's properties, and connect the signal in the character's signal-connection function.
- For components involved in disabling other components (Sleep component, Chicken/scare component), add the affected component to the disabling-initiator component, and connect the signal in the character's signal-connection function.
- Except for the cases above, all other custom signals must be connected by the character body itself, in the corresponding initialization function within `_ready()`.

__A normally-deployed (Norm) character's death must occur via the HP component draining its HP to zero — directly deleting the character is prohibited.__
